Historical design/review notes. See [the current implementation](REALTIME.md) and [release notes](docs/release-0.5.0.md).


Superseded by [the alpha.3 integration review](APTEVADB_ALPHA3_REVIEW.md): both remaining findings below are resolved in the published alpha.3 tag.

13 October 2026. Published tag: `v0.2.0-alpha.2`, commit `41115aaa65a1c81de471e7f6e94c1db9f833f3af`.

The original integer-filter and large-document failures are fixed. Adapter development can proceed against alpha.2, with a fresh snapshot/index cursor per request and an explicit experimental capability contract. Full interchangeability with the Database app is not green: an index cursor repositioning defect and a remaining physical index-size mismatch need resolution.

## Remaining cursor defect

A reused `IndexCursor` can skip records when `SeekAfter` returns to an earlier saved position. With a descending numeric index containing keys `2`, `1`, `0`:

1. Read key `2` and copy its `Position()` bytes.
2. Traverse the remainder of the cursor.
3. Call `SeekAfter` with the saved position.
4. Expected key `1`; alpha.2 returns key `0`, with no error.

A freshly opened cursor given the same position returns key `1` correctly. The regression is independently reproduced in `TestIndexCursorRepositionToEarlierSavedPosition`.

`IndexCursor.seekPosition` delegates an arbitrary exclusive seek to `Cursor.move`. The leaf optimization in `Cursor.treeStep` starts from the cached slot for the previous location, so it can skip eligible entries when the new position moves backward. Resetting the leaf cache for explicit position seeks, or validating/recomputing the cached search slot, is the likely repair. Test both SeekAfter and SeekBefore, forward/backward jumps, exhausted cursors, multiple leaves and retained snapshots.

The planned adapter already creates a fresh cursor for each signed page request. That avoids this reproduced case during initial integration, but the public native cursor behavior should still be fixed.

## Remaining index-size mismatch

Alpha.2 raises `MaxKeySize` to 4,032 bytes, but that is the cap on a complete native index-entry key, including the indexed value, appended primary key and engine framing. The app permits the primary key and index tuple under separate limits: 2,048 and 4,096 bytes respectively.

A concrete valid app input is still rejected:

- Text primary key: 1,500 bytes, or 1,504 bytes in the app's canonical JSON key.
- Indexed text value: 3,000 bytes, or a 3,003-byte app index tuple.
- Native compound index creation: `ErrKeySize` because the combined physical entry exceeds 4,032 bytes.

The remaining difference affects full parity even though ordinary primary keys now fit. Choose one explicit resolution: extend the native physical index representation to accommodate the app's combined limits, or expose narrower limits for the experimental adapter. An adapter must not silently truncate/hash an ordered tuple or lower SQLite/Pebble limits.

The error text also still says “key must be 1..1024 bytes,” despite the updated constant. This is a diagnostic issue, separate from the actual cap.

## Adapter responsibilities and next validation

Typed schemas/catalogs, wire integer conversion, patch-style upserts, version checks, scopes/permissions and signed pagination remain adapter work. Native DDL remains outside transactions; schema catalog publication needs an explicit atomic metadata mechanism or durable intent/recovery protocol.

The published feature timings use asynchronous loading/WAL settings and unequal cache models; they are useful observations, but do not replace a comparison of the new adapter with matched durability and identical responses. Reuse the earlier direct-driver harness after integration and add secondary-index pages, concurrent clients, startup/recovery and memory measurements.

The format-7 upgrade is permanent. All probes here used disposable data; no installed app database was opened or upgraded.
